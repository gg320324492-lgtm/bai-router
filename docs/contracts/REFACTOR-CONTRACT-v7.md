# REFACTOR-CONTRACT v7 — 修「弹框与横幅并存」（v1.0.55）

给实施 agent 的边界契约。**单工作项**，但根因分析很关键，请先读完再动手。

---

## 现象（用户实拍）

手动检查更新时，屏幕中央弹出对话框（v1.0.54），**右下角同时又有一条横幅**。

## 我之前判断错了，真因在这里

v1.0.54 我以为「同一件事被渲染了两遍」，改成互斥。**但真因是两个并行的更新事务**。

证据来自 `%APPDATA%\bai-router\app.log`：

```
05:14:01  手动检查发现新版本 v1.0.53，等待用户确认（不自动下载）
05:14:10  用户确认安装，开始下载 v1.0.53          ← 用户点了「立即安装」
05:20:38  手动检查发现新版本 v1.0.54，等待用户确认（不自动下载）
05:20:41  用户确认安装，开始下载 v1.0.54          ← 又点了
```

**关键：05:14:10 之后，日志里再没有任何 v1.0.53 的完成记录。** 那次下载一直挂着。

于是 05:20:38 用户再点「检查更新」时：
- `updateState` 还是 `phase:"downloading", version:"1.0.53"` 的旧状态 →
  走 `manualCheckUpdate` 的 early-return 分支，补发 `{...updateState, manual:true}` → **弹框打开**
- 但紧接着 `update-available` 带来了 **v1.0.54** → 又一次事件
- 屏幕上因此同时有：**v1.0.54 的弹框** + **v1.0.53 的下载横幅**

用户截图佐证：弹框写「发现新版本 v1.0.54」，横幅是进度条，底栏版本 v1.0.53。

**所以 v1.0.54 的互斥修复没做错，只是没覆盖这个场景——它是对的但不够。**

---

## 需要修的三件事

### 1. `installReadyUpdate()` 在下载中重复调用会启动重复下载

`src/main.js` 约 618 行：
```js
if (updateState.phase === "downloading") {
  logMain("用户确认安装，开始下载 v" + ...);
  autoUpdater.downloadUpdate()...
  return;
}
```
用户点两次「立即安装」→ 调两次 `downloadUpdate()`。electron-updater 对同一次下载有幂等保护，
但**跨版本**（1.0.53 下到一半又去下 1.0.54）状态会乱。

**要求**：下载中再次点「立即安装」时，不要盲目再调一次。要么直接忽略并给出提示，
要么先确认目标版本变了再处理。**你判断哪种更合理并说明理由。**

### 2. 检查更新时，若已有下载在进行，旧事务要先收尾

`manualCheckUpdate()` 约 676 行。用户在下 v1.0.53 的途中又点检查更新，
拿到 v1.0.54 后，**v1.0.53 的下载没有被取消、也没有被标记为过期**，
它还在往 `download-progress` 里喂数据。

**要求**：让「当前待处理的版本」只有一个。当发现的新版本与正在下载的版本**不同**时，
旧的那个应当被放弃（取消下载或至少标记作废），避免两个事务并存。

`electron-updater` 的 `autoUpdater` 没有公开的 cancel API——**如果确实无法取消，
你可以在渲染层/状态层做「只认最新事务」的处理**（例如给每次检查打一个递增的序号，
旧序号的事件直接丢弃）。**你选方案并说明理由。**

### 3. 渲染层：横幅与弹框不应该是「互斥」，而应该是「同一个事务的两个视图」

v1.0.54 我做的互斥把两者当成一件事，但实际它们可能是**两件事**。
真正的规则应该是：**横幅和弹框永远显示同一个事务**。

**要求**：渲染层要能识别事件属于哪个事务（版本号天然就是标识），
**只渲染当前事务**；旧事务的事件直接忽略。这样无论主进程发什么，
屏幕上都不会同时出现两个不同版本的通知。

## 接口约定

事务标识用 **版本号**（`state.version`）。渲染层记住「当前正在显示哪个版本」，
只处理与之匹配的事件；版本变化时整体切换（收掉旧的、开新的）。

**若你认为需要额外字段**（例如主进程显式给一个事务 id），**先说明理由**——
但要保证两端一致。
